# Sysmon collection, a custom rule, and clock troubleshooting

## Question

Could I trace a harmless process execution from Windows to a Wazuh alert, and explain the evidence?

I installed Sysmon 15.22, confirmed Sysmon64 was running, and configured the agent to collect Microsoft-Windows-Sysmon/Operational. Local events included IDs 1 (process creation) and 5 (process termination). The dashboard then showed Sysmon-derived alerts. Service status alone was not enough; received events provided the collection evidence.

Evidence: screenshots [25](../screenshots/25-windows-sysmon-installed.png), [27](../screenshots/27-windows-sysmon-local-events.png), and [28](../screenshots/28-windows-sysmon-events-in-wazuh.png).

## Investigating the parent process

One alert involved PowerShell exporting security policy with secedit, reading ResetLockoutCount, and removing its temporary secpol.cfg file. The parent was wazuh-agent.exe and the account was SYSTEM. This was consistent with the agent's configuration-assessment activity and cleanup. I did not classify every PowerShell alert as harmless based on that one record.

[Parent-process evidence](../screenshots/29-sysmon-wazuh-assessment-powershell-alert.png)

## Why my first whoami search returned nothing

Running whoami.exe in Windows produced a local Sysmon process event, but searching the dashboard by executable and process GUID returned no matching alert. A manager-side text search also matched the audit event generated by my own sudo search, which was not the target Windows event.

The manager had logall and logall_json disabled and log_alert_level set to 3. The installed base Sysmon event-1 rule, 61603, had level 0. These settings help explain why recording an event locally does not guarantee an alert appears in the dashboard. I did not establish that the original missing event reached the manager or identify its final matched rule.

The base-rule details came from terminal output. Screenshot 31 shows surrounding rules and the original local_rules.xml example; despite its original filename, it does not visibly establish rule 61603's level.

## Custom detection and live verification

I backed up local_rules.xml, preserved its existing example rule, and added [rule 100100](../configs/whoami-rule.xml). It inherits from 61603 and matches an image path ending in whoami.exe, case-insensitively, at level 3.

The analysisd configuration check returned without an error. A synthetic JSON attempt in wazuh-logtest decoded as generic json and did not produce the expected matching phase; I do not count it as a successful rule test.

After activating the rule, a new whoami.exe execution on Windows produced the expected live alert. The details showed the executable, labadmin account, PowerShell parent, and Sysmon channel. This verified the collection-to-alert path for that test.

- [Live alert, rule 100100](../screenshots/32-wazuh-whoami-custom-rule-live-alert.png)
- [Executable, user, and parent details](../screenshots/33-wazuh-whoami-custom-alert-details.png)

The command is legitimate and harmless. This deliberately broad lab rule detects execution, not malicious intent, and would need context and tuning for operational use.

## Clock correction and retest

Windows reported Local CMOS Clock, no successful synchronization, and UTC approximately three hours ahead of the synchronized Ubuntu server. Its Pacific display timezone was separate from the actual UTC discrepancy.

I configured Windows Time to use time.windows.com. The first resync returned no time data. Later stripchart replies differed by less than 0.09 seconds, and the status command confirmed successful NTP synchronization. Stripchart itself was a measurement, not proof that it performed the correction.

| Fresh test evidence | Time on October 11, 2026 |
| --- | --- |
| PowerShell UTC printed before whoami | 21:04:46 UTC |
| Sysmon utcTime | 21:04:46.047 UTC |
| Dashboard alert | Approximately 17:04:46 EDT |

This new test showed agreement after timezone conversion. Correcting the clock did not rewrite old timestamps, and it does not prove the earlier missing alert was caused by clock skew.

Evidence: [unsynchronized status](../screenshots/34-windows-time-not-synchronized.png), [successful synchronization](../screenshots/35-windows-time-synchronized.png), [fresh alert comparison](../screenshots/36-wazuh-whoami-alert-time-verified.png).

## Outcome

Sysmon collection and the custom rule worked in a live controlled test. The rule remains enabled for practice. Earlier screenshots preserve the clock problem as it occurred; old event times should not be treated as a reliable timeline without qualification.
